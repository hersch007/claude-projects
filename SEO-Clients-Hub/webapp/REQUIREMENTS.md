# SEO Platform — Requirements & Scope

Status: draft v2 — 2026-09-15 (open questions resolved, ready for Phase 0 design)
Owner: Richard (GroupRB)

## 1. Purpose

Replace the current CLI/`.bat`-driven audit workflow (`seo-tool/audit.js` + per-client
JSON configs + Claude Code skills) with a web app that runs SEO audits and generates
client reports, aiming for feature parity with **Ubersuggest**, **SEObility**, and
**Moz** wherever that's achievable without paid third-party data.

## 2. Audience & Use Case

- **Internal agency tool only.** Used by Richard/GroupRB team members to run audits
  and produce reports for their own clients (the businesses already under
  `clients/`). Not a customer-facing self-serve product.
- No external sign-up, no billing, no multi-tenant customer isolation. Auth just
  needs to gate access to the internal team.

## 3. Current State (what already exists and will be reused/replaced)

| Piece | Today | Role going forward |
|---|---|---|
| `seo-tool/audit.js` | Node/Cheerio crawler, run via `node audit.js <slug>`, prompts for provider (1-4) and manual metrics | Becomes the audit **engine**, called by the web app instead of the CLI |
| `seo-tool/gsc.js` / `gsc-auth.js` | Google Search Console API pull | Reused as-is for rank/visibility data |
| `seo-tool/clients/*.json` | Per-client crawler config (url, brand color, output dir, GSC property, ignore paths) | Migrates into a proper DB table |
| `clients/<Name>/CLIENT-BRIEF.md`, `*-SEO-AUDIT-*.md`, `*-MASTER.docx`, `*-Prospect-Report*.docx` | Files generated by Claude Code skills (`new-seo-client`, `run-seo-audit`) | Audit *content* (11-section structure, scoring rubric) becomes the report data model in the app; file generation becomes an export function, not the primary output |
| 4 "provider" letterheads (Start Advertising, Start Performance, Parts of Practice, GroupRB) | Picked interactively per run | Becomes a settings/branding record per report |
| SEO Health Score rubric (Technical 20 / On-page 20 / Content 20 / E-E-A-T 20 / Local 10 / Schema 10) | Manual scoring guide in `new-seo-client` skill | Becomes the app's scoring algorithm, applied consistently instead of per-run judgment |

## 4. Goals

1. Run an audit from a browser, not a terminal — no `node`, `npm`, or `.bat` files.
2. Persist audit history per client so scores and issues can be **tracked over time**
   (trend charts), not just overwritten each run.
3. One dashboard listing all clients, their latest score, and last audit date.
4. Keep report output (HTML/PDF/Word) at least as good as what the skills produce today.
5. Cover the core feature set of Ubersuggest/SEObility/Moz **that is achievable on
   free/owned data sources** (see §6). Do not fake or estimate data (e.g. invented
   keyword volumes) where a real free source doesn't exist — omit the feature instead.

## 5. Non-Goals (explicitly out of scope for v1)

- Public/customer self-serve accounts, billing, or plan tiers.
- Backlink index / Domain Authority-style scoring — no viable free data source
  (Common Crawl is partial/stale and not worth building against for v1).
- Third-party keyword-volume or SERP-rank-tracking data that requires a paid API
  (DataForSEO, Ahrefs, SEMrush, Moz Links API). Can be revisited later if the
  agency decides to license one — see §9.
- White-labeling for resale to other agencies.
- Mobile app.

## 7. Deferred / Phase 2+ candidates

- Keyword Planner API integration — GroupRB MCC account (169-720-1017) exists;
  **needs Google Ads API access + developer token approval** before this can start.
- Scheduled/automatic re-crawls (e.g. weekly) with email/Slack summary of score changes.
- Competitor comparison (crawl a client-named competitor URL side by side) — fully
  achievable on free sources, just not in v1 scope.
- Content/readability grading beyond basic checks.
- If the agency later decides to pay for a data API (DataForSEO etc.), backlink
  index and estimated keyword volume/difficulty can be added without changing the
  rest of the architecture — the crawler and DB schema should leave room for it
  (e.g. a nullable `backlink_count` field) but nothing should block on it now.

## 8. Non-Functional Requirements

- **Data sensitivity:** client sites, GSC data, and generated reports are
  confidential business data — internal auth required (no public deployment
  without login), HTTPS only.
- **Reliability:** a failed crawl (site down, timeout, robots-disallowed) must
  fail clearly in the UI, not silently produce a partial/wrong score.
- **Performance:** a full-site crawl (up to ~60 pages, matching current
  `max_pages` default) should complete in the UI without the user needing to
  keep the tab open indefinitely — needs a background job, not a blocking
  request.
- **Portability:** should run both locally (agency machine) and on a small
  hosted server — no hard dependency on a specific OS (current `.bat` files are
  Windows-only; the web app should not be).

## 9. Proposed Architecture (high level — to be detailed in a separate design doc)

- **Hosting: decided — small hosted server**, not local-only. The team needs to
  trigger audits and view the dashboard from anywhere, and background crawl jobs
  need to run without a machine staying on. Implies the app needs real
  authentication (internal team login) and HTTPS from day one, not just
  local-network trust.
- **Backend:** Node.js, reusing `audit.js`'s crawl logic as a library rather than
  a CLI script; crawl runs as a background job (queue) so the UI isn't blocked.
- **Database:** replaces `seo-tool/clients/*.json` and the file-per-report model —
  clients, audit runs, findings, and scores as rows so history/trends are queryable.
  Given hosted (not local-only) deployment, plan for Postgres rather than SQLite
  so the DB isn't tied to a single server's local disk.
- **Frontend:** dashboard (client list + trends) + per-client audit view + report
  export button. Reuses the existing 11-section structure and scoring rubric as the
  data model, not a redesign of the report content. Each client's settings page
  includes a manual "add historical score" entry (date + score, optionally per
  category) so older audits can be logged into the trend chart by hand — see §7.
- **Report generation:** keep the existing Word/PDF generation approach (the `docx`
  package scripts already used by the skills), triggered from the app instead of
  written/run/deleted as throwaway scripts each time.

## 11. Proposed Phases

- **Phase 0 — Pilot:** wrap `audit.js` in a minimal web UI (trigger a crawl,
  view the report) for one existing client, no DB yet — validates the crawl
  engine works headless/server-side without the CLI's interactive prompts.
- **Phase 1 — MVP:** client dashboard, DB-backed audit history, Health Score
  computed consistently, Word/PDF export matching current report quality,
  migrate all current clients in.
- **Phase 2 — Enhancements:** Keyword Planner integration — **unblocked**,
  Explorer-level Google Ads API access approved (see §10a) — scheduled
  re-crawls, trend charts/alerts on score drops.
- **Phase 3 — Stretch:** competitor comparison, and (only if the agency decides
  to pay for it) a licensed data API for backlinks/DA.
